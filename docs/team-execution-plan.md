# 3–4 人團隊分工與執行計畫

## 一、目標與原則

團隊需在有限時間內完成三件事：

1. 恢復一份可測試、可部署的程式基線。
2. 將產品聚焦為 1～14 日主動波段交易者的資訊提煉工具。
3. 導入可彈性規劃、但具有固定輸出契約的 Agent 工作流。

產品與架構依據：

- [Agent 彈性與穩定輸出設計](./agent-flexibility-output-contract.md)
- [主動交易者資訊產品設計](./active-trader-information-product.md)
- [資料來源目錄](./data-source-catalog.md)
- [異常訊號分析規劃](./anomaly-signal-plan.md)

團隊分工遵循：

- 一人不擅長開發，**不分配任何程式撰寫、Git、除錯、測試自動化或 AWS 部署任務**。
- 非開發工作不是輔助雜務，而是產品定義、資料可信度抽查、使用者驗收及競賽呈現的明確責任。
- 共用契約先定義，再讓資料、Agent 與前端平行開發。
- 每個高衝突檔案同一時間只有一位 owner。
- 先完成單一垂直切片，再擴充所有工具與題型。

## 二、目前的第一優先事項

目前工作區曾檢查到下列檔案處於未解決合併衝突狀態：

- `lambda/agent.py`
- `lambda/report.py`
- `tests/test_report.py`
- 部分 `.kiro/specs/**/requirements.md`

`python -m py_compile` 會在 `agent.py` 的衝突標記失敗。因此所有新功能前應先：

1. 暫停多人修改上述檔案。
2. 指定「技術整合負責人」統一解決衝突。
3. 由另一位開發者 review 合併結果。
4. 執行編譯與目標測試，建立可運行基線。
5. 基線通過後，才切分後續開發分支。

此階段不交由非開發成員執行。

## 三、四人團隊配置

### 角色 A：技術整合與部署負責人（開發）

**主要責任**

- 解決現有 Git 合併衝突並建立穩定基線。
- 定義並維護 `AnalysisPlan`、`ResearchResult`、`ReportModel` 等共用 Schema。
- 負責 `handler.py`、錯誤處理、整體時間預算與模組串接。
- 管理整合分支、code review、版本標記與回退方式。
- 打包及更新 Lambda、S3 前端與必要 AWS 設定。
- 執行部署前 smoke test 與部署後端到端驗證。

**主要交付物**

- 可編譯、測試通過的整合版本。
- Schema 與 API contract。
- 可重複執行的部署步驟。
- AWS 版本、環境變數與部署驗證紀錄。

**主要檔案範圍**

- `lambda/handler.py`
- `lambda/config.py`
- 共用 schema／model 模組
- 部署腳本與整合測試

### 角色 B：資料工具與品質負責人（開發）

**主要責任**

- 盤點並實測資料來源的時效、額度、錯誤率及 fallback。
- 統一工具回傳欄位：時間、視窗、單位、交易對、provider、endpoint 與 freshness。
- 維護價格、衍生品、新聞、鏈上、總經等工具。
- 實作決定性計算、資料拼接、相容性與異常偵測。
- 建立工具 timeout、rate limit、錯誤降級及單元測試。
- 確保 Evidence 可回溯並封存必要原始資料。

**主要交付物**

- 工具能力與資料品質矩陣。
- 主動交易者第一個垂直切片所需的三類可靠資料。
- 工具測試、失敗案例與資料相容性說明。
- 可被 Agent 使用的標準化工具結果。

**主要檔案範圍**

- `lambda/tools/`
- `lambda/evidence.py`
- `lambda/storage.py`
- 對應工具測試

### 角色 C：Agent、驗證與報告負責人（開發）

**主要責任**

- 實作 Planner、受控執行器、可選 Sub-agent 與 Synthesis Agent。
- 控制工具白名單、Agent 輪數、token 與時間預算。
- 實作完整 evidence ID、資料新鮮度、事實引用及投資建議檢查。
- 將模型輸出改為 Schema 驗證的中間格式。
- 實作 `ReportModel` 到 Markdown 的決定性 Renderer。
- 建立題型、部分工具失敗、無資料、無效 JSON 與 timeout 測試。

**主要交付物**

- 可依題目動態選擇工具的 Agent 工作流。
- Validator 與保守 fallback 報告。
- 格式穩定的 ReportModel 及 Markdown 報告。
- Agent 與報告層自動化測試。

**主要檔案範圍**

- `lambda/agent.py`
- `lambda/report.py`
- `lambda/export.py`
- Agent／Report 測試

### 角色 D：產品、研究與競賽呈現負責人（非開發）

此角色不負責任何程式開發。

**主要責任**

- 定義 1～14 日主動波段交易者 persona、情境與痛點。
- 訪談或邀請目標使用者試用，整理需求優先順序。
- 用表格維護資料來源名稱、用途、授權、費用、可信度及一手／二手分類。
- 以瀏覽器人工抽查 Evidence：網址是否可開啟、時間是否合理、引用片段是否支持判斷。
- 撰寫首屏資訊順序、卡片文案、空狀態與錯誤訊息規格。
- 使用部署完成的 UI 執行手動驗收，不修改前端程式。
- 整理 Demo 腳本、提案簡報、AWS 架構敘事、錄影流程與評審問答。
- 記錄每次測試中的「看不懂、找不到、無法信任」問題，交給開發者修正。

**明確不分配的任務**

- 不修改 Python、HTML、JavaScript、Shell 或設定檔。
- 不處理 Git branch、merge、conflict、commit 或 pull request。
- 不撰寫或維護自動化測試。
- 不操作 Lambda 程式碼更新、S3 上傳、IAM、Bedrock 或環境變數。
- 不負責 API 除錯、log 分析或資料轉換腳本。
- 不單獨變更正式資料來源或付費 API 設定。

**主要交付物**

- Persona 與三個核心使用情境。
- 版面線框、資訊優先順序與文字規格。
- Evidence 人工抽查清單。
- 使用者驗收紀錄與問題優先級。
- 提案簡報、Demo 腳本、錄影 checklist 與評審問答。

## 四、三人團隊配置

若只有三人，維持一位非開發成員，不把其工作轉為程式任務：

### 開發者 A：整合、Agent 與部署

- 解決衝突、維護 Schema。
- 實作 Planner、Validator、ReportModel 與 Renderer。
- 負責 Handler、整合測試與 AWS 部署。

### 開發者 B：資料工具、前端與品質

- 維護資料工具、決定性計算與 Evidence。
- 依產品規格實作 Dashboard。
- 負責工具、前端及端到端測試。

### 成員 C：產品、研究與競賽呈現（非開發）

- 工作內容與四人配置的角色 D 相同。
- 不因人數減少而承接任何程式、Git、測試自動化或部署任務。
- 若開發量超出兩位開發者容量，應縮減 MVP 範圍，而不是把開發工作轉交給此成員。

### 三人版縮減原則

依序保留：

1. 價格／技術、衍生品／流動性、事件催化劑的 BTC 垂直切片。
2. Evidence、Execution Log、固定 ReportModel 與 Validator。
3. 單幣多源與假設驗證題。
4. 雙幣比較。
5. 其他鏈上、社群及進階機構資料。

時間不足時先延後第 4、5 項，不犧牲證據追溯、格式驗證與穩定部署。

## 五、工作階段

### 階段 0：恢復基線

**開發工作**

- A 解決 Git 衝突。
- B 或 C review 衝突結果。
- 執行編譯、目標測試與本地 smoke test。
- 保存可回退版本。

**非開發工作**

- 整理命題必要交付物與評分項目 checklist。
- 不接觸衝突檔案或 Git。

**完成條件**

- 核心 Python 檔案可編譯。
- Agent／Report／Handler 目標測試通過。
- 本地可產生 report、Evidence List、Execution Log。

### 階段 1：共同定義產品與契約

**全員共同決策**

- 確認 TA 為 1～14 日主動波段交易者。
- 選定 BTC 第一個垂直切片。
- 確認 ReportModel 欄位與首屏資訊順序。
- 確認禁止輸出的投資建議類型。

**開發工作**

- A／C 定義 JSON Schema、API contract 與假資料。
- B 定義工具標準欄位與資料 freshness 規則。

**非開發工作**

- D 產出 persona、使用情境、低擬真線框和驗收語句。
- D 人工整理每個資料來源對交易者的用途與可信度。

**完成條件**

- 三份 Schema 經全員確認。
- 使用假資料即可渲染完整報告與 Dashboard。
- 非開發成員能依畫面說出市場狀態、信心與主要矛盾。

### 階段 2：BTC 垂直切片

**開發工作**

- B 完成價格／技術、衍生品／流動性、事件催化劑資料鏈。
- C 完成 Planner、驗證、整合與 ReportModel。
- A 串接 Handler、S3 與前端 API。

**非開發工作**

- D 用實際輸出抽查 Evidence 與來源。
- D 進行人工可讀性測試，記錄理解時間與疑問。
- D 完成 Demo 的第一版敘事。

**完成條件**

- 一題可從輸入一路完成至 Dashboard 和下載檔案。
- 所有關鍵引用使用完整 evidence ID。
- 部分資料來源失敗時仍可產出保守報告。

### 階段 3：題型與 Sub-agent 擴充

**開發工作**

- 增加假設驗證和雙幣比較。
- 最多啟用 2～3 個與題目相關的 Sub-agent。
- 建立時間、token、throttling 與 fallback 測試。
- 擴充其他幣種與必要資料來源。

**非開發工作**

- D 準備不同題型的人工驗收問題。
- D 比較多次輸出的可讀性、一致性與可信度。
- D 檢查是否出現投資建議或過度自信語句。

**完成條件**

- 不同題型使用相同 API 與 ReportModel。
- 不相關的資料維度不會被強制填滿。
- 矛盾與資料不足在畫面中可見。

### 階段 4：部署、演練與交付

**開發工作**

- A 執行 Lambda／S3 更新及部署後 smoke test。
- B／C 檢查 CloudWatch、工具失敗與報告品質。
- 建立可重複部署與回退步驟。

**非開發工作**

- D 依真實部署網址執行完整使用者驗收。
- D 錄製完整流程、整理簡報、架構敘事與評審問答。
- D 確認所有交付連結與文件可被評審理解。

**完成條件**

- 連續演練可在 15 分鐘內完成。
- 正式網址可完成輸入、分析、報告與下載。
- 簡報、影片、GitHub、Evidence、Log 和報告齊全。

## 七、協作與 Git 規則

- 先建立 issue／任務，寫明 owner、輸入、輸出及完成條件。
- `agent.py`、`report.py`、共用 Schema 等高衝突區域指定單一 owner。
- 每個分支只處理一個明確主題，不混合無關重構。
- 合併前由另一位開發者 review，且必須附測試結果。
- 不在未解決衝突上繼續新增功能。
- 部署由 A 統一執行，其他成員不直接覆蓋正式 Lambda 或 S3。
- API key 不放入文件、簡報、測試資料或 Git。
- 非開發成員透過共享文件、設計稿、表格與部署後網址協作，不要求使用 Git。

## 八、每日同步格式

每日同步控制在 15 分鐘，每人只回答：

1. 昨天完成了哪個可驗證輸出？
2. 今天要交付什麼？
3. 目前被哪個契約、資料或人員阻塞？
4. 是否影響 15 分鐘執行限制或 Demo 穩定性？

非開發成員同步的是研究、線框、查證、測試與簡報交付物，不需要回報程式進度。

## 九、Definition of Done

一項功能只有同時滿足以下條件才算完成：

- 有明確使用者價值或命題要求對應。
- 輸入、輸出與錯誤格式符合契約。
- 開發工作有自動化測試或最小 smoke test。
- Evidence 可回溯，時間、視窗與單位可理解。
- 非開發成員能依驗收步驟在部署後 UI 重現結果。
- 失敗、資料不足及矛盾狀態有合理呈現。
- 不含投資建議、秘密資訊或無來源的事實。
- 文件、Demo 說法與實際系統行為一致。

## 十、下一步清單

1. A 接手並解決目前合併衝突。
2. 其他開發者 review，跑編譯與目標測試。
3. 非開發成員完成 persona、三個使用情境和首屏線框。
4. 全員用一場短會議確認三份 Schema 與 BTC 垂直切片。
5. 開發者依契約分成資料、Agent／報告與整合三軌。
6. 非開發成員同步進行資料來源人工查證、UI 驗收規格與 Demo 敘事。
7. 垂直切片部署後，先完成一次完整演練，再決定是否擴充 Sub-agent 或更多資料源。
