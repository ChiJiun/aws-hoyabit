# 主動交易者資訊產品設計

## 一、產品定位

### 目標使用者

第一版聚焦於**持有與觀察週期約 1～14 日的主動波段交易者**，而不是高頻或分鐘級日內交易者。

原因：

- 目前具備近五年 Daily OHLCV 基準資料，適合歷史百分位與波段環境判斷。
- 現有工具以 REST API、新聞、鏈上、衍生品與總經資料為主，適合事件驅動分析。
- Agent 完整分析可使用數分鐘，無法保證高頻交易所需的毫秒級低延遲。
- 命題要求可信、多源、可解釋的市場分析，而不是自動下單或即時交易訊號。

若未來定位改為日內交易者，需另行規劃分鐘 K、WebSocket、即時清算、spread、order-flow 與低延遲資料管線，不應直接沿用本版 SLA。

### 價值主張

> 在資訊碎片化的市場中，讓主動交易者快速看懂「目前是什麼市場狀態、哪些訊號最值得注意、各來源是否互相矛盾，以及什麼變化會推翻目前判斷」。

系統是資訊提煉與風險辨識工具，不提供買賣、倉位、目標價或自動下單建議。

## 二、使用者要完成的工作

主動交易者進入系統後，應能在短時間回答：

1. 現在是趨勢、盤整、波動壓縮，還是波動爆發環境？
2. 市場是否出現槓桿擁擠、流動性變差或參與度下降？
3. 價格、衍生品、鏈上、新聞與總經訊號是否一致？
4. 有哪些即將發生的事件可能改變市場狀態？
5. 哪些資料新鮮、哪些過期、哪些無法取得？
6. 目前判斷的信心為何，什麼條件會使它失效？
7. 每項重要判斷要去哪裡查證？

## 三、資訊來源優先順序

詳細來源、API 與組合訊號請見 [data-source-catalog.md](./data-source-catalog.md)；異常門檻與背離規則請見 [anomaly-signal-plan.md](./anomaly-signal-plan.md)。本節定義產品層級與使用方式。

### Tier 1：短期市場狀態

這一層直接描述主動交易者面對的價格、波動、流動性及槓桿環境，應優先取得。

| 資料 | 目的 | 現有或候選來源 | 時效要求 |
|---|---|---|---|
| 價格與 OHLCV | 報酬、區間、趨勢、成交量 | baseline CSV、Binance、CoinGecko | 當日或更近 |
| 決定性技術指標 | ATR%、布林帶寬、ADX、實現波動、量能 Z-score、相關性 | 本地 quant 計算 | 跟隨價格資料 |
| 衍生品 | Funding、OI、多空比、taker ratio | Hyperliquid、Binance Futures | 分析執行當下或最近週期 |
| 期權波動 | DVOL、IV、Put/Call | Deribit（BTC／ETH） | 分析執行當下 |
| 現貨流動性 | Order book 深度、spread、可用深度 | Binance spot | 快照需標示時間 |
| 市場輪動 | 市佔率、BTC dominance、跨幣相關性 | CoinGecko、quant | 當日 |

### Tier 2：短期催化劑與事件風險

| 資料 | 目的 | 來源 | 時效要求 |
|---|---|---|---|
| 官方公告 | 升級、服務中斷、安全事件、代幣或治理變化 | 專案官方部落格、GitHub releases | 近 7～30 日 |
| 新聞 | 市場敘事、事件密度、新聞與價格背離 | Google News RSS、公開媒體 | 近 24 小時～14 日 |
| 監管文件 | ETF、執法、監管與機構事件 | SEC EDGAR 等一手來源 | 依題目期間 |
| 總經日曆 | CPI、FOMC、利率與已知事件窗口 | FRED、官方日曆 | 顯示下一事件時間 |
| 預測市場 | 事件機率與現貨反應是否錯位 | Polymarket | 快照需標示時間 |

新聞摘要本身不是結論；官方與一手來源優先，媒體內容應交叉驗證。第三方分析師文章不可成為唯一關鍵依據。

### Tier 3：確認、否定與中期背景

| 資料 | 目的 | 來源 |
|---|---|---|
| 鏈上活躍度 | 檢查價格是否與實際網路使用脫鉤 | mempool.space、Etherscan、Helius、Blockscout、XRPL |
| DeFi 與穩定幣 | 資金流、TVL、穩定幣供給與價格背離 | DefiLlama |
| 情緒 | 極端情緒、情緒急變與價格錯位 | Fear & Greed、公開社群 |
| 開發活動 | 區分短期敘事與持續建設 | GitHub |
| 機構／鏈上指標 | MVRV、NVT、機構持倉等補充證據 | Coin Metrics、CFTC COT 等 |

對 1～14 日交易者，這一層通常是確認或否定訊號，不應無條件與即時價格、槓桿、流動性資料等權。

## 四、資料處理邏輯

### 4.1 題目與時間範圍正規化

先從輸入辨識：

- 幣種及比較對象。
- 題型：多源整合、假設驗證、比較分析或其他。
- 觀察期間及資料截止點。
- 必須回答的子問題。
- 使用者明示與隱含的風險維度。

若題目沒有指定時間，產品預設以「近期 1～14 日市場狀態」解讀，並在報告中揭露。

### 4.2 先做資料新鮮度與相容性檢查

每筆標準化資料除命題要求的 Evidence 欄位外，內部應保留：

- `as_of`：資料代表的時間。
- `timeframe`：例如 1d、8h、快照。
- `window`：例如最近 14 日、90 日。
- `unit`：USD、百分比、枚數等。
- `symbol` 與交易對。
- `provider` 與 endpoint／query。
- `freshness_status`：fresh、stale、unknown。
- `comparability_notes`：與其他幣種或來源比較的限制。

不同鏈的交易數、地址數或區塊窗口不可直接當成同一尺度比較；如無法正規化，報告需明確標示「只能觀察各自變化，不能比較絕對值」。

### 4.3 決定性計算與異常偵測

以下內容由程式計算，不交給 LLM 心算：

- 報酬率與價格區間。
- ATR%、ADX、布林帶寬、實現波動率。
- 成交量 Z-score 與歷史百分位。
- 相關係數及其視窗。
- Funding、OI 或情緒等時間序列的變化率與百分位。
- 單源異常門檻。

呈現數字時固定包含：

> 絕對值 + 歷史百分位或比較基準 + 時間視窗 + 資料截止時間。

### 4.4 跨來源交叉驗證

Agent 應尋找與題目相關的：

- 一致訊號：不同來源支持相同市場狀態。
- 背離訊號：例如價格上漲但量能下降、OI 上升但波動壓縮。
- 反方證據：能否推翻原始假設。
- 證據不足：資料失敗、過期、單位不相容或僅有單一來源。

不能為了湊固定來源數而呼叫無關工具。來源多樣性是品質觀察點，不是每題必須平均分配的配額。

### 4.5 形成市場狀態，而非交易指令

最終結論描述：

- 市場 regime。
- 趨勢、波動、流動性及槓桿狀態。
- 關鍵催化劑與風險。
- 支持與反對證據。
- 信心與推翻條件。
- 後續應觀察的變數。

不得輸出買進、賣出、進出場點、倉位比例、槓桿倍數或目標價。

## 五、固定輸出模型

ReportModel 的完整架構與驗證責任見 [agent-flexibility-output-contract.md](./agent-flexibility-output-contract.md)。產品層至少需要：

| 區塊 | 內容 |
|---|---|
| market_state | regime、時間範圍、信心、資料截止時間 |
| key_findings | 最重要的 3～5 項發現 |
| supporting_signals | 支持目前判斷的訊號及 evidence IDs |
| contradicting_signals | 背離與反方證據 |
| catalysts | 已知事件、時間及可能影響面向 |
| risks | 流動性、槓桿、資料與事件風險 |
| invalidation_conditions | 會推翻目前判斷的可觀察條件 |
| watch_items | 後續追蹤變數，不含交易指令 |
| limitations | 資料失敗、過期與比較限制 |

## 六、結果版面

### 6.1 首屏：十秒內理解市場狀態

建議順序：

1. 幣種、分析問題、觀察期間與資料截止時間。
2. 一句話市場狀態，例如「波動壓縮、槓桿增加、方向尚未確認」。
3. 信心等級與造成信心下降的首要原因。
4. 三個最重要訊號。
5. 一個最重要的矛盾或警告。

首屏不可只顯示抽象分數；每個狀態都應能展開查看資料值與 Evidence。

### 6.2 訊號矩陣

每張訊號卡固定包含：

- 訊號名稱與層級：顯著、關注、常態或資料不足。
- 方向與市場含義，但不轉換為買賣建議。
- 數值、百分位、視窗與資料時間。
- 支持／反對目前判斷。
- 完整 evidence ID。
- 資料來源與查證連結。
- 限制及可比性說明。

維度應由題目與實際證據動態產生，不固定為五維雷達。若需要視覺摘要，優先顯示「已取得、過期、失敗、不可比較」等資料品質狀態。

### 6.3 催化劑時間線

依時間排序顯示：

- 已發生且仍影響市場的事件。
- 即將發生的官方、監管與總經事件。
- 預測市場機率或市場定價變化。
- 事件的重要性、來源和不確定性。

### 6.4 矛盾、風險與推翻條件

這一區需與支持訊號同等顯眼：

- 哪兩個來源互相矛盾。
- 為何目前暫時採信其中一方。
- 哪項新資料會改變取捨。
- 哪些資料缺失限制了信心。

### 6.5 Evidence 抽屜與下載

前端展開後顯示：

- `source`／`source_url`。
- `fetched_at` 與資料 `as_of`。
- `content_reference`。
- `related_claim`。
- 查詢條件、endpoint、交易對、地址、視窗及單位。
- 原始資料或 Evidence List、Execution Log 的下載連結。

## 七、資料品質與內容驗收

### 必須通過

- 報告所有關鍵事實都使用完整且存在的 evidence ID。
- 每個比較結論均揭露單位、視窗及可比性。
- 首屏能在十秒內說明市場狀態、信心與主要矛盾。
- 來源時間與題目期間一致，過期資料被清楚標示。
- 至少有一段交叉驗證、背離、反方證據或證據不足說明。
- Evidence 可從畫面追溯到來源及取得時間。
- 沒有投資建議或第三方完整分析的直接轉述。

### 建議追蹤的產品指標

- 使用者找到前三項關鍵訊號所需時間。
- 使用者能否正確說出目前判斷的限制。
- 報告有效 evidence ID 引用率。
- 新鮮資料占實際使用證據的比例。
- 工具成功率與降級後仍能完成報告的比例。
- 完整流程在 15 分鐘內完成的比例。

## 八、第一個垂直切片

在擴充所有題型前，先完成一條端到端流程：

> BTC 過去兩週市場狀態：價格與技術面 + 衍生品與流動性 + 事件催化劑。

此切片需完整涵蓋：輸入、規劃、資料取得、異常計算、交叉驗證、Evidence、ReportModel、Dashboard、下載與 Execution Log。完成後再擴展鏈上、雙幣比較及其他幣種。
